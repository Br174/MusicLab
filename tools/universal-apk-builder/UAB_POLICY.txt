UNIVERSAL APK BUILDER POLICY

CORE ARCHITECTURE
1. The Universal APK Builder core must remain project-neutral. Do not hardcode MusicLab, GeoVision, repository names, branches, workflow IDs or package names inside the core engine or provider adapters.
2. Project-specific behavior belongs in the project adapter files (for example uab-project.env, uab-router.env and optional .uab/pre-build.sh / .uab/post-build.sh hooks).
3. Standard Android Gradle projects should build without custom hooks. Projects that require generated sources, code generation, wrappers or other preparation may provide a project-specific pre-build hook without changing the core engine.
4. The same core engine must be reusable for MusicLab, GeoVision and future Android Gradle projects.

MANDATORY APK REQUEST FLOW
1. Every request to obtain, download, generate, rebuild or deliver an APK/ZIP for any UAB-enabled Android project MUST use this flow. Do not invent or prefer alternate delivery/build routes before UAB.
2. ARTIFACT-FIRST is mandatory. Before starting any build, check whether the current requested project/branch/commit already has a ready APK/ZIP in the configured UAB artifact registry. If status is ready and the manifest commit matches the requested/current source commit, return the APK and ZIP immediately and DO NOT rebuild them unless the user explicitly asks for a rebuild.
3. If no matching ready artifact exists, start the provider router with the default order: local/current chat environment -> GitHub Actions free allowance -> Codemagic/UAB robust fallback.
4. The first two providers must use fast availability checks. If a provider is clearly unavailable because of missing toolchain, authorization, free quota, runner, service or configuration, fail fast and immediately continue to the next provider. Do not spend minutes discovering an unavailable provider.
5. A fast preflight is different from a real build. Once a provider has passed preflight and the Android build has genuinely started, allow the build to finish normally.
6. If a real build fails because of project/code/signing/dependency errors, STOP and diagnose the project instead of repeating the same broken build on other providers.
7. If a provider fails only for infrastructure/quota/authorization/runner reasons before meaningful build steps run, immediately continue to the next provider.
8. Email, AppDeploy, manual mailbox searches and ad-hoc artifact recovery routes are not part of the normal APK request flow.
9. The user must never need to remember or restate this flow. The AI/router is responsible for applying it automatically on every APK/ZIP request.

DEFAULT APK BUILD PATH
1. Route APK requests through tools/universal-apk-builder/route-build.sh when the router environment is available.
2. Provider order is read from each project's uab-router.env and can be changed without modifying application code or the Builder core.
3. Default provider order: local/current chat environment -> GitHub Actions -> Codemagic.
4. The local/current environment gets a quick preflight first. If the Android toolchain or required project files are unavailable, fail fast and continue to the next free provider instead of wasting build time.
5. Provider adapters are generic. Project-local provider adapters may optionally be added under .uab/providers/ and override a core adapter of the same name.
6. A provider may be skipped when its free quota, authorization, runner or service is unavailable.
7. If a build actually starts and fails because of project/code/signing/dependency errors, STOP and diagnose it instead of wasting minutes on another provider.
8. Collect APK + SHA256 + ZIP under dist/uab whenever the active provider uses the UAB build engine.

UNIVERSAL ARTIFACT DELIVERY
1. APK/ZIP delivery must remain project-neutral and reusable across MusicLab, GeoVision and future projects.
2. Email, AppDeploy and a Codemagic API token must not be required to recover normal UAB artifacts.
3. Codemagic delivery uses the project-neutral publisher tools/universal-apk-builder/publish-github-manifest.py after the local UAB build has created APK/ZIP files under dist/uab.
4. The publisher uploads the actual APK/ZIP files directly from the build machine to a central private GitHub Releases registry configured by UAB_MANIFEST_REPOSITORY.
5. Each project gets its own stable release tag, by default uab-{project}-latest, and its own manifest path, by default uab-artifacts/{project}/latest.json, so projects never overwrite one another.
6. The publisher replaces the assets of that project's latest release, records size and SHA256, then updates latest.json with the release and asset download URLs.
7. The central registry must not use GitHub Actions. Release uploads and latest.json updates are direct GitHub REST API operations and must not trigger a build provider.
8. UAB_GITHUB_MANIFEST_TOKEN must be stored only as a protected provider secret and should have write access only to the central artifact registry repository, not to source-code repositories.
9. The normal chat retrieval path is: read the project's latest.json through the connected GitHub account -> expose the current APK/ZIP release URLs in chat.
10. Provider-specific notification channels such as email may exist only as optional backup and must not be part of the required artifact retrieval path.
11. A delivery failure must not invalidate an APK/ZIP that was successfully built; delivery and compilation are separate statuses.

PARALLEL LAB INSTALLATION
1. LAB/test builds should install side-by-side by default instead of overwriting a previously installed LAB.
2. The UAB core generates a unique build identity when UAB_PARALLEL_INSTALL is enabled.
3. Each project adapter declares its base application ID and how the generated ID is injected into that project. Project-specific variable names must not be hardcoded in the core.
4. Production/MADRE builds keep a stable application ID unless explicitly requested otherwise.
5. Existing project-specific parallel-install rules, such as GeoVision LAB package separation, must be preserved and may map to the same UAB contract through the project adapter.
6. The visible LAB app name may include a short build identifier so multiple installed test versions can be distinguished easily.

COST SAFETY
- Paid fallback is forbidden: UAB_PAID_FALLBACK must remain "never".
- Never buy minutes, enable billing, increase a budget, or use paid overage automatically.
- GitHub Actions may be used automatically as a FREE fallback when included usage is available.
- Codemagic may be used automatically while its free allowance is available.
- Additional free providers may be added by creating another provider adapter and placing its name in UAB_PROVIDER_ORDER.
- If all free providers are unavailable, stop and report the blocker.
- API tokens and signing credentials must never be committed to the repository; provide them only through protected environment/secrets.

USER EXPERIENCE
Bruno should only need to request the app modification/build. He should not have to remember provider names, GitHub Actions, Codemagic, Gradle, OpenCurt or project-specific preparation steps. The router selects the available free build path and the project adapter performs any required preparation automatically. Whenever the active environment can materialize the final artifacts, APK and ZIP should be returned directly in the chat. When a matching artifact is already ready, it must be returned immediately without rebuilding. When Codemagic is used, the chat should retrieve the latest project manifest from the central GitHub registry instead of relying on email, AppDeploy or Codemagic API credentials. LAB builds should arrive as separately installable apps unless Bruno explicitly asks for an update of an existing package.
