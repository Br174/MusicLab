LOCAL FALLBACK CONTRACT
- MotorLab activates before substantive project work when project/software-build context is visible.
- First user-visible line: ⚙️ MotorLab attivo
- Load project hook and project-specific central continuity ledger automatically.
- Reconcile ledger with newer live repo/ref/head/provider/job/artifact evidence before choosing a starting point.
- Classify newer live events as application work, MotorLab control-plane activity, external automation or unknown-before-reconcile before changing app lifecycle identity.
- Preserve active operation, verified progress floor, completed step, pending verification and next safe step across chat ids.
- No recurring activation or transfer prompt is required.
- Live newer evidence outranks stale ledger, older registries and memory summaries.
- Unfinished work continues through Resume Recovery under Watchdog coordination.
- Manual ⚡ uses save-then-resume and monotonic recovery-floor rules.
- Project Continuity updates at material state transitions and safe turn handoff when central write access exists.
- A missed expected write-through is a Root Cause Closure problem; manual alignment alone is not definitive closure.
- MotorLab-only control-plane commits should suppress unrelated CI/build triggers when the provider supports a safe skip mechanism, and repository trigger filters should exclude MotorLab-only paths where appropriate.
- Change Compatibility Guard applies before writes.
- Foreground Stall Guard applies before substantial/risky phases.
- Only one writer may mutate the same project/ref/resource scope.
- Project-native/domain engines are preserved and never replaced by MotorLab activation.
- Load MOTORLAB_FAST_ITERATION_NO_SPIN_V1.txt when central access exists; this local bundle preserves its mandatory r12 invariants when central access is unavailable.

VISUAL SEMANTICS
- preferred format: <emoji> <canonical label> — <context>;
- repeated-fireworks/repeated-lightning counts are obsolete as user-facing level codes;
- 🎆 marks an action/phase/milestone completed, not necessarily the whole request;
- 💯 is reserved only for true end-to-end completion after all requested verification/delivery is complete;
- ✅ requires Root Cause Closure permission, not symptom-only repair;
- 🔍 means solution/cause search, not confirmed closure;
- 🧩 requires compatibility/preflight evidence;
- 🐢 means slow but still live/legitimate, not automatically stalled;
- 💭 means high-level operational analysis and never private chain-of-thought;
- ⏳ means legitimate external provider/job/service waiting;
- 🧪 means tests/verification are still in progress;
- 🔄 means synchronization/reconciliation is still in progress;
- ⚡ remains for actual wake/recovery/health action.

HARD NUMERIC PROGRESS VISIBILITY - R11+
Classic form remains:
Progresso MotorLab: <N>%
For a substantial active/pending/new operation:
- after the activation banner, establish/reconstruct and display an evidence-based N% before entering long opaque work;
- every meaningful user-facing operational status MUST include the current N% when the surface permits;
- before a long build/test/provider phase, show the current N%;
- material provider/job phase changes repeat or advance the N% rather than remaining silent;
- repeated same percentage is correct when state changes without a newly verified milestone;
- do not invent progress merely for visibility;
- a new chat/turn does not reset or suppress the percentage.

ROOT CAUSE CLOSURE - R11+
For every real defect/anomaly/stale state/unexpected trigger/failure:
- contain/correct the immediate symptom safely;
- determine why it occurred using evidence;
- distinguish confirmed cause, leading hypothesis, external cause or unknown cause;
- correct/contain the causal mechanism when possible;
- inspect the smallest relevant recurrence surface;
- add prevention/regression protection when justified;
- do not use ✅ Problema risolto from a one-off retry, restart or manual alignment alone;
- root-cause/prevention work remains part of the operation and can keep progress below 100%.

PROJECT CONTINUITY / LIVE EVENT CLASSIFICATION - R11+
- a stale ledger is reconciled from newer live evidence but unexpected missed write-through also opens Root Cause Closure;
- MotorLab/control-plane-only commits/jobs do not silently create a new app LAB/MADRE/CANDIDATA or new app progress scale;
- if control-plane-only changes unexpectedly trigger app build/release workflows, classify the trigger as a causal defect and correct trigger hygiene when safe.

CONTROL-PLANE CI SUPPRESSION - R11+
For commits that modify only MotorLab control-plane metadata such as `.motorlab/**` or `MOTORLAB_PROJECT_HOOK.txt`:
- use a provider-supported CI skip marker/mechanism when safe and available;
- prefer repository path filters that exclude MotorLab-only metadata from application build/release workflows;
- do not suppress CI when the same commit also changes application source/configuration that legitimately requires validation;
- verify that prevention does not hide required tests for real app changes.

FAST ITERATION + NO-SPIN - R12+
Ownership remains unchanged: Velocity Layer owns acceleration/risk scaling; Foreground Stall Guard owns handoff preparation; Background Execution owns persistent jobs; Watchdog owns health; Resume Recovery owns continuation.

NO-SPIN HANDOFF
- Once a persistent executor has accepted a job and MotorLab has recorded operation/ref/job id/progress/checkpoint/next-safe-step, an ordinary foreground chat must not poll indefinitely waiting for completion.
- Default maximum is two consecutive unchanged foreground provider/job status probes after durable identity is established.
- If the job is healthy/queued/running/waiting externally, transition the foreground cycle to HANDOFF_COMPLETE; do not cancel the external job.
- On the next available cycle, inspect the same recorded job id before any duplicate start or write.
- UI “processing” or a spinner is not a heartbeat and must not be treated as evidence of live MotorLab execution.
- If no persistent executor exists, do not promise background continuation; use bounded foreground segments and checkpoints.

RISK-SCALED FAST ITERATION
- For isolated LAB correction loops before Bruno device/user acceptance, use LOW/MEDIUM/HIGH risk classification from actual change scope.
- LOW: scope/diff + appropriate build/static validity + smallest relevant smoke + testable artifact. Full project regression is not automatic.
- MEDIUM: LOW checks + targeted affected tests when they exist + adjacent smoke + testable artifact. Unrelated full suites are not automatic.
- HIGH: full applicable regression from the start.
- CANDIDATA/MADRE always retain full adapter-defined regression, exact identity/replay, artifact and approval gates regardless of earlier LAB risk class.
- Avoid separate expensive compile/test/build phases when they substantially duplicate one another without distinct verification value.
- Reuse valid dependency/build caches and incremental outputs when source/toolchain identity allows it.

MUSICLAB R12 DEFAULT PROFILE
- isolated copy/style/static UI: LOW;
- bounded navigation/state/UI feature behavior, Cover/Originali screen logic, contained AI/API orchestration: MEDIUM unless blast-radius evidence raises it;
- core playback service/queue/audio engine, package/signing/update identity, database migration, Meld upstream integration, lifecycle/build infrastructure, concurrency/background integrity: HIGH.
- `:app:testFossDebugUnitTest :innertube:testDebugUnitTest` is promotion/high-risk grade by default and is not mandatory on every LOW/MEDIUM correction iteration unless affected-test mapping requires it.
- UAB preflight/build remains the canonical path for requested isolated installable MusicLab LAB APK/ZIP artifacts.
- A Bruno-reported device defect preserves the prior LAB and starts the next isolated LAB; do not rerun unrelated verified work.
